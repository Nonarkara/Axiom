## Found, changed, verified

### The index printed the same header four times

The reading room's index prints a group header — name and count — whenever the
cluster changes from one entry to the next. The catalogue array had been
appended to in build order (simsmartcity, 淼燊的上海, TDV, TechHunt…), so the
header **CITY DASHBOARDS · 23 appeared four times** and **LAB · 23 twice**, in
the first screen of the index. Each header restated a count the reader had just
read. It looked like seven short sections; it was five.

Nothing threw. Every id, number, cluster and cluster size was correct, and
`npm test`, the plate gate and 191 journeys were green throughout, because none
of them looked at what order the headers fall in.

- **Repair:** the catalogue is grouped by cluster, in order of first appearance.
  Within a cluster the order is unchanged.
- **Guard:** `tests/catalogue.test.mjs` — *the reading-room catalogue is grouped,
  so each cluster header prints once*. Proved by mutation: against the previous
  catalogue it fails, naming the entry that reopens a group.
- **Cost of the repair:** zero geometry. The 71 existing reading-room routes
  re-measured identical to the committed baseline.

### Two version badges contradicted the picture beside them

The new AirDash capture prints **"AirDash 3.0"** in its own header; the card's
badge said **v1.1.0**. Yala's live header reads **v0.1.0**; the badge said
**v1.2.0**. A thumbnail and a badge on one card disagreeing is the system
claiming more certainty than it has. Both now match what the live systems print
(read from the live pages, not typed), in the card badge and in the reading
room's stack plate.
